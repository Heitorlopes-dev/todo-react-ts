Documentação da Aplicação: To-do List

Esta documentação detalha a arquitetura, fluxos principais, estrutura de dados e regras de segurança da aplicação.

🏗️ 1. Arquitetura

A aplicação segue uma arquitetura client-server baseada em BaaS (Backend as a Service), eliminando a necessidade de um servidor próprio para gerenciar regras de negócios e banco de dados.

  • Frontend: Single Page Application (SPA) desenvolvida com React 19, TypeScript e Vite.
  • Backend: Firebase (Authentication para gestão de identidades e Cloud Firestore para armazenamento de dados).
  • Gerenciamento de Estado Global: Utiliza a Context API do React (AuthContext) para estado de autenticação e dados do usuário. Hooks customizados (como useTasks) são usados para abstrair as regras de chamadas ao banco de dados.
  • Roteamento: O React Router (HashRouter) orquestra o roteamento client-side, com componentes de proteção bloqueando acessos indevidos.

🔐 2. Fluxo de Login

O sistema suporta duas formas de autenticação: Email/Senha e Provedor Google. O fluxo de sessão é gerido pelo AuthContext.

🗂️ 3. Estrutura do Firestore

O banco de dados (NoSQL) é hierarquicamente organizado em torno do uid (User ID) para garantir isolamento e segurança.

erDiagram USERS { string uid PK string role "Padrão: 'user'" } TASKS { string id PK string name "1 a 500 caracteres" boolean completed "Inicia false" timestamp createdAt } ACTIVITIES { string id PK string action string category string description timestamp createdAt } USERS ||--o{ TASKS : "possui subcoleção" USERS ||--o{ ACTIVITIES : "possui subcoleção"
  • /users/{userId}: Documento raiz do usuário onde, por exemplo, o campo role é armazenado.
  • /users/{userId}/tasks/{taskId}: Subcoleção de tarefas. Campos validados de forma estrita para manter a integridade dos dados (somente booleanos para completado, limites de strings no título, etc).
  • /users/{userId}/activities/{activityId}: Subcoleção de histórico e auditoria (logs de login, logout, criação de tarefas, exclusão de conta).

🛡️ 4. Regras de Segurança (Firestore Rules)

As regras do Firestore formam a principal linha de defesa contra acessos não autorizados e payloads inválidos.

Importante: A API do Firebase é exposta no lado do cliente. As firestore.rules são as únicas responsáveis por impedir que um usuário mal-intencionado manipule dados alheios ou envie dados inválidos (ex: uma string no lugar de um boolean).

Principais restrições:

  1. Validação de Schema em Criação/Atualização: As tarefas exigem os campos exatos durante a criação. O tipo dos campos é verificado e validado estritamente.
  2. Append-only para Atividades: A regra da coleção activities declara bloqueio de atualização. Isso garante que ninguém (nem mesmo o dono) consiga modificar um log do histórico após ele ter sido criado.
  3. Escopo Default Fechado: Qualquer acesso não previsto nas regras é negado por padrão.

🚦 5. Fluxo de Permissões (Admin vs User)

A aplicação diferencia usuários comuns de administradores com base no campo role no documento do usuário em /users/{uid}.

As regras contam com helpers de verificação como isOwner(userId) e isAdmin() para cruzar o uid da requisição com os dados do banco.

Tabela de Permissões (Matriz de Acesso)

Recurso (Firestore) Ação Permissão user (Dono) Permissão admin
User Doc (/users/{uid}) Leitura (read) ✅ (Apenas o próprio) ✅ (Qualquer user doc)
User Doc (/users/{uid}) Atualização (update) ✅ (NÃO pode alterar o role) ✅ (Altera qualquer campo)
Tarefas (/tasks/{id}) CRUD completo ✅ (Apenas as próprias) ❌ (Privacidade garantida)
Atividades (/activities/{id}) Leitura (read) ✅ (Apenas as próprias) ✅ (Ver histórico de todos)
Atividades (/activities/{id}) Criação (create) ✅ ❌ (Não cria logs pros outros)
Atividades (/activities/{id}) Deleção (delete) ✅ (Limpar próprio histórico) ❌
Dica de Segurança: A proteção da mudança de role é estrita através da função affectedKeys do Firestore. Isso previne o "Privilege Escalation", ou seja, garante que um usuário comum jamais conseguirá se tornar administrador usando requisições maliciosas. Somente outro administrador ou um script backend de manutenção podem alterar a role.
